# LabAssist AI — Architecture

LabAssist AI is a single application. One FastAPI backend exposes one chat endpoint, and one
**orchestrator** decides, per request, which of the three knowledge mechanisms to use:

| Mechanism | What it holds | Where it lives | How it reaches the model |
|-----------|---------------|----------------|--------------------------|
| **RAG** | Uploaded PDF/TXT/DOCX documents | Chunks in PostgreSQL, BGE-M3 vectors in FAISS (`backend/data/faiss`) | Top-k passages retrieved per question, tagged `[D1]`, `[D2]`… |
| **CAG** | Approved FAQs, procedures, policies | `knowledge_items` + prepared context in `cag_contexts` | One prepared text block, identical for every request of the same audience and KB version, tagged `[KB<id>]` |
| **MAG** | Per-user preferences | `memories` (always filtered by `user_id`) | Short list under "USER MEMORIES (preferences only, not laboratory evidence)" |

```
React (Vite) ──SSE/JSON──► FastAPI /api/chat/stream
                               │
                               ▼
                     Orchestrator (services/orchestration)
             ┌────────────────┼──────────────────┐
             ▼                ▼                  ▼
        RagService        CagService         MagService
   (FAISS + PostgreSQL)  (prepared context)  (user-scoped rows)
             └────────────────┼──────────────────┘
                              ▼
                  Prompt builder → Ollama (mistral) → streamed tokens
                              │
                              ▼
          Message + sources + context_info + metrics → PostgreSQL
```

## Request flow (`Orchestrator.run`)

1. Resolve or create the conversation (owned by the current user only) and store the question.
   A retry after a failed generation reuses the existing question instead of duplicating it.
2. **MAG capture**: if the message is an explicit request ("remember that…", "souviens-toi que…",
   "تذكر أن…") and the user has enabled memory, the sensitive-data filter runs and the memory is stored
   or refused. The outcome is reported to the user.
3. **Plan** (`router.plan_sources`): decide which mechanisms to consult from the selected mode.
4. **Gather**: retrieve passages (kept only above `RAG_MIN_SCORE`), fetch the prepared CAG context,
   select relevant memories.
5. **Build prompt** (`prompts.build_messages`): fixed safety system prompt + CAG block first (stable prefix),
   then history, then a user turn containing document excerpts, memories, per-answer instructions and the question.
6. **Stream** tokens from Ollama over SSE (`meta` → `token`* → `done` | `error`).
7. **Finalise**: mark which sources were actually cited (`[D#]`, `[KB#]` found in the answer), store the
   assistant message with `architectures_used`, `sources`, `context_info`, and record a metric row.

Sources shown in the UI are always the passages/entries that were actually retrieved — they are never
generated by the model. The "cited" flag only indicates whether the model referenced them.

## Modes

| Mode | Consulted | Notes |
|------|-----------|-------|
| `auto` | RAG if documents are indexed (and the question isn't small talk); CAG if approved entries match or the question is about a lab topic; MAG if memory is enabled and relevant memories exist | `architectures_used` reports what was actually used, e.g. `["rag","cag"]` or `["llm"]` |
| `rag` | Documents only | Instructs the model to say so when no passage passes the threshold |
| `cag` | Prepared approved context only | |
| `mag` | Memories only | The model is told not to answer lab policy/medical questions in this mode |
| `hybrid` | All three, in separate prompt sections | Evidence (documents, approved knowledge) is kept apart from preferences (memories) |

## Safety rules enforced in the orchestrator

- **No invented policy/citations**: the system prompt forbids facts not present in `[KB#]`/`[D#]` blocks;
  when nothing relevant was retrieved for a lab question the model receives an explicit
  "say it is not available in the approved sources" instruction.
- **No diagnosis**: questions that look like diagnosis/result-interpretation requests get an extra
  instruction to refer to a physician.
- **Conflicts**: the prompt instructs the model to show both sources, flag the conflict, prefer approved
  knowledge for official policy and recommend confirming with the laboratory. (The sample patient guide
  intentionally contains an older Saturday schedule than the approved knowledge to exercise this.)
- **Outdated**: knowledge entries past `review_due` are labelled `REVIEW OVERDUE` in the context and flagged
  `outdated` in the sources; document excerpts carry their version and last-update date.
- **Missing**: if a mechanism is unavailable (e.g. embeddings down) the answer still proceeds with a warning in
  `context_info.warnings`.

Detection of conflicts is delegated to the model through these instructions; LabAssist does not claim to
detect semantic contradictions programmatically.

## CAG: application-level reuse vs. model KV-cache reuse

**Application-level context reuse (implemented and measured by LabAssist)**

- Approved entries are rendered once per *audience* (`public` = patients, `staff` = staff + public entries)
  and *knowledge-base version* into a deterministic text block with a SHA-256 hash.
- The block is cached in memory and persisted in `cag_contexts`, so it survives restarts.
- Every approve/unapprove/archive/delete — or edit of an approved entry — creates a new row in
  `knowledge_base_versions` and deletes all prepared contexts. The next request rebuilds them.
- `context_info.cag.application_context_reused` is `true` when the block came from the cache (`memory` or
  `database`) and `false` when it was just built.
- **Context-window limit**: entries are added in priority order until the token estimate reaches
  `min(CAG_MAX_CONTEXT_TOKENS, OLLAMA_NUM_CTX − LLM_MAX_ANSWER_TOKENS − 1500)`. Entries that do not fit are
  listed as `excluded_item_ids` in the admin UI. Token counts are conservative estimates (≈3 chars/token);
  real counts come from Ollama after generation.

**Model KV-cache reuse (not controlled by LabAssist)**

- The KV cache is internal to the inference engine (Ollama / llama.cpp). LabAssist cannot create, address or
  persist it.
- What LabAssist does is make reuse *possible*: the system prompt and the CAG block are placed first and are
  byte-identical across requests, and `OLLAMA_KEEP_ALIVE` keeps the model loaded. llama.cpp may then skip
  re-evaluating the shared prefix.
- The UI shows Ollama's `prompt_eval_count` ("prompt evaluated") next to LabAssist's estimate of the full
  prompt. A value much lower than the estimate indicates the engine reused cached prefix tokens; LabAssist
  reports this as an observation, never as a guarantee.

## MAG: privacy rules

- Memory is **opt-in** per user (`users.memory_enabled`, default off). When disabled nothing is stored and
  existing memories are not used.
- Only explicit requests or manual entries are stored — ordinary questions are never mined for memories.
- Allowed categories: language preference, communication style, general preference, topic of interest.
- Refused content: email addresses, phone numbers, long identifiers, dates, lab values with units,
  credentials, and health/special-category terms (FR/EN/AR). The user is told why.
- Retention: each memory expires `MEMORY_RETENTION_DAYS` after its last update; expired rows are purged at
  startup, hourly, and before listing. Maximum `MEMORY_MAX_PER_USER` per user.
- Isolation: every query filters on `user_id`; another user's memory id returns 404. There is no admin
  endpoint that reads memory content (the dashboard only shows a total count).

## Access control

| Role | Chat | Own memory | Documents | Knowledge drafts | Approve knowledge | Users / metrics | LabVision (own analyses) |
|------|------|-----------|-----------|------------------|-------------------|-----------------|--------------------------|
| patient | ✓ (public documents & public knowledge only) | ✓ | – | – | – | – | – |
| staff | ✓ (public + staff-only sources) | ✓ | ✓ | ✓ (edits to approved entries return them to draft) | – | – | ✓ |
| admin | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Public endpoints: `GET /api/health`, `POST /api/auth/login`, `POST /api/auth/register` (always creates a
patient; can be disabled with `ALLOW_SELF_REGISTRATION=false`). Everything else requires a JWT.

## Logging and metrics

- Logs contain method/path/status/latency and component events; a redaction filter masks anything that looks
  like a password, token or Authorization header. Message content is never logged.
- `request_metrics` stores: timestamp, path template, status, latency, user *role*, requested mode,
  architectures used, model, prompt/completion token counts reported by Ollama, error type. No user id, no text.

## Data model (PostgreSQL)

`users`, `conversations`, `messages`, `documents`, `document_chunks` (primary key = FAISS vector id),
`knowledge_items`, `knowledge_base_versions`, `cag_contexts`, `memories`, `request_metrics`,
`labvision_analyses` (computed results per uploaded dataset, owned by one user, `expires_at` retention),
`labvision_findings` (machine-generated findings + separate human review fields).

## LabVision AI

`backend/app/services/labvision/` is independent of the chat orchestrator:

```
upload ─► parsing (validate, decode, read every cell as text) ─► DatasetStore (memory, TTL, per user)
                                                                     │  POST /api/labvision/datasets/analyze
                                                                     ▼
          profiling ─► quality checks ─► anomaly detection ─► score, charts, recommendations
                                                                     │
                                       labvision_analyses + labvision_findings (no raw file)
```

- Endpoints: `POST /api/labvision/datasets/preview`, `POST /api/labvision/datasets/analyze`,
  `GET|DELETE /api/labvision/analyses/{id}`, `GET /api/labvision/analyses/{id}/findings` (+ `findings.csv`),
  `GET /api/labvision/analyses/{id}/report` (PDF), `POST /api/labvision/analyses/{id}/explanation`,
  `PATCH /api/labvision/findings/{id}/review`, plus the optional cleaning preview / cleaned copy on an in-memory dataset.
- Access: staff and admin only; every query filters on the owner, so another user's analysis, finding or dataset id
  returns 404. Errors return a generic message; logs contain counts and ids only, never cell values.
- Findings are capped per analysis (`LABVISION_MAX_FINDINGS`, highest severity first); counts and metrics are exact.
Schema changes are managed with Alembic (`backend/alembic`).
